# 创作者投放数据服务

服务登记多来源事件、业务主体及现有摘要，并保存发布报告的原始内容。在原始事件
之上提供一套可解释的活动归因与结算口径，让市场与财务看到同一批事件如何产生
不同期间的结果。示例数据为虚构记录。

需要 Python 3.10 或更新版本；仅依赖标准库。

运行测试：python -m unittest discover -s tests -v
编译检查：python -m compileall -q analytics tests
本地演练：python -m analytics --database demo.sqlite3 --fixture fixtures/campaign_sample.json

## 模块分工

- `store.py`：来源事件与修订，不可变、只追加；同一来源同一事件的更高修订替代旧修订。
- `identity.py`：外部身份到内部分析主体（顾客、创作者）的映射，无法映射的事件列为未归属。
- `metrics.py`：原始事件计数与通用金额，仅表示观察，不代表结算结果。
- `decisions.py`：已发布报告的正文与摘要哈希。
- `domain.py`：活动目录（预算、点击/曝光回看窗口）与创作者参加活动的结算比例。
- `attribution.py`：把曝光、点击、订单、退款解释为每笔订单唯一的归因结论与待核。
- `settlement.py`：按期间封存结算依据，并把封存后的退款与归属纠正表达为后续期间调整。
- `campaign_analytics.py`：同一套归因结论的市场视图（漏斗、创作者表现）与财务视图
  （预算占用、未结算预算、待核金额）。

## 归因口径（每笔订单最多一个结算对象）

1. 曝光与点击载荷携带 `campaign`、`creator`；订单携带 `campaign`、`order_id`、
   `amount`；退款携带 `order_id`、`amount`，支持部分退与多次退，净额不为负。
2. 只考虑活动回看窗口内、订单发生之前的同顾客触达：有点击取最后一次点击
   （`last_click`），否则取最后一次曝光（`last_exposure`）。完整触达路径与
   每条触达是否入窗随结论快照留痕。
3. 结论分四类：
   - `attributed` 已归因：唯一创作者，按活动结算比例计算应付，可进入结算。
   - `pending_review` 待核：同刻多创作者并列、胜出创作者未参加活动、活动未登记、
     重复订单等确定性规则无法打破的情形；金额隔离，不进结算、不占预算，
     经人工裁决（`resolve_review`）后才可结算。
   - `unattributed` 未归因：窗口内无合格触达，永不结算。
   - `invalid` 无效：订单金额无效或顾客主体无法映射。
4. 人工裁决独立保存并优先于自动规则；裁决之后的事件修订不会覆盖人工结论，
   历史时点（`as_of` 早于裁决时间）仍呈现裁决前状态。归属纠正走 `redecide`，
   每次裁决都在裁决历史中留痕。
5. 归因是可重算的纯解释：来源事件永不改写，每次重算完整重放事件流；结论变化时
   旧版本进入归因历史，可逐单回查。

## 结算与期间调整

- 结算单按期间哈希封存（`seal_settlement`）：封存水位（watermark）前已观测的事件
  与已作出的裁决才进入该期间；水位只进不退。单内每行随附当时的归因快照
  （触达路径、退款事件、净额与应付），封存内容不可变，可用 `verify_settlement` 回查。
- 订单首次进入结算单后即被冻结。封存之后到达的退款、事件修订或归属纠正不回改
  旧单，而在新期间生成调整行：
  - `refund_adjustment`：同一创作者净额变化，差额通常为负（追回）。
  - `reversal` + `attribution_adjustment`：归属纠正，先从原创作者全额追回，
    再向新创作者补付，期间合计为净影响。
  - `hold_reversal` / `reversal`：订单转入待核、未归因或事件被修订删除时追回。
- 待核与未归因订单不占用预算；人工裁决后在其后的期间结算。
- `order_trace(order_id)` 给出一笔订单的当前结论、归因历史、裁决历史与跨期间
  结算链，同一笔变化在不同期间的结果可逐行对照。
